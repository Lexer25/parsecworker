================================================================================
 ParsecIntegrationClient — модуль интеграции СКУД Артонит и СКУД Парсек
 История версий
================================================================================

Версия задаётся в одном месте — ParsecIntegrationClient/ParsecIntegrationClient.csproj
(<Version>, <AssemblyVersion>, <FileVersion>). Установщик берёт её из версии файла
службы, поэтому при выпуске правится только csproj.
Новые записи добавляются сверху.

--------------------------------------------------------------------------------
4.1.4 — 31.10.2026
--------------------------------------------------------------------------------

Запрещён запуск второго экземпляра программы:
  * при старте процесс захватывает именованный мьютекс
    Global\ParsecIntegrationClient.SingleInstance и удерживает его до выхода;
  * если экземпляр уже работает (служба + консоль, две копии в разных каталогах,
    второй сеанс RDP), новый процесс завершается с кодом 2 и пишет в журнал и
    stderr: "Второй экземпляр ParsecIntegrationClient не запущен: ... (PID ...)";
  * раньше две копии читали одну PARSEC_QUEUE и дублировали операции в Парсеке;
  * --version не блокируется, проверку поставки можно делать при работающей службе;
  * после аварийного завершения следующий запуск проходит: мьютекс освобождает ОС,
    AbandonedMutexException обрабатывается;
  * если у пользователя нет права создавать глобальные объекты, но на машине видна
    работающая копия, запуск блокируется по имени процесса; если копий нет, защита
    действует в пределах сеанса (в журнал пишется предупреждение).

Затронутые файлы: Services/SingleInstanceGuard.cs (новый), Program.cs.

4.1.3 — 31.10.2026
--------------------------------------------------------------------------------

Исправлено: операция 8 (удаление категории доступа у сотрудника) больше не падает
с "Critical error in RemoveIdentifierPeople: Value cannot be null. (Parameter 'g')",
если сотрудника или категории доступа уже нет в базе СКУД Артонит.

Что было не так:
  * запрос "select p.guid, an.guid from accessname an, people p where
    p.id_pep = ... and an.id_accessname = ..." не находил пару и возвращал пустой
    результат (в журнале — "91 Результат запроса пустой");
  * DatabaseService.Get в этом случае отдавал не null, а пустой объект модели,
    поэтому проверка "model == null" не срабатывала;
  * код шёл дальше и падал на new Guid(null). Сообщение об ошибке ничего не
    объясняло, задача уходила в повтор, а проход очереди останавливался
    ("ГЛОБАЛЬНАЯ ОСТАНОВКА"), хотя удалять было нечего.

Что сделано:
  * DatabaseService.Get<T>: пустой результат запроса возвращает null, NULL в
    колонках переносится в поля как null (раньше ToString() на NULL давал
    NullReferenceException при чтении строки);
  * операции 7 и 8 проверяют пару GUID (сотрудник GUID_PEP + категория доступа
    GUID_ACCGROUP) до любого обращения к Парсеку; если данных нет — предупреждение
    в журнал (сообщения 114 и 840) и штатное завершение:
      - в PARSEC_QUEUE строка получает статус 5 «пропущено»;
      - понятный текст причины пишется в PARSEC_QUEUE.error_text и в журнал:
        "Удаление категории доступа не требуется: в базе СКУД Артонит нет пары
        ID_PEP=... и ID_ACCESSNAME=... — сотрудник или категория доступа
        отсутствуют, либо у них не заполнен GUID. В Parsec по этим данным
        обращаться не с чем, задача завершена без ошибки";
      - очередь продолжает обрабатываться, следующие события не блокируются;
  * ProcessAccessCatAddition / ProcessAccessCatRemoval получают уже разобранные
    Guid: повторного new Guid(строка из БД) больше нет;
  * AddOrg / SaveOrgUnit: добавлена проверка model == null (следствие изменения
    DatabaseService.Get).

Затронутые файлы: Services/DatabaseService.cs, Services/ParsecService.cs.

4.1.0 — 28.10.2026
--------------------------------------------------------------------------------

Срок действия идентификатора и новая операция 11 (изменение свойств
идентификатора):
  * тип объекта в SOAP выбирается по наличию TIMEEND, а не TIMESTART;
  * таблица выбора: обе даты → IdentifierTemp(TIMESTART, TIMEEND);
    TIMESTART = NULL → VALID_FROM = текущие сутки 00:00:00;
    TIMEEND = NULL → VALID_TO = 31.12.9999; обе NULL → идентификатор без дат;
  * некорректный срок (TIMESTART > TIMEEND) — ошибка с кодом 27, текст в журнале
    и в PARSEC_QUEUE, проход очереди останавливается;
  * ACTIVE передаётся в Парсек через SetIdentifierExtraData (ACTIVE > 0 →
    ENTRY_LIMIT = -1, ACTIVE = 0 → ENTRY_LIMIT = 0), в том числе при добавлении
    карты (операция 9);
  * смена ID_CARDTYPE: 1 → 2 — удаление идентификатора (операция 10),
    2 → 1 — добавление (операция 9);
  * операция 11 (ChangePersonIdentifier): срок в Парсеке сравнивается с базой
    (допуск 1 секунда), остальные свойства идентификатора сохраняются;
  * триггеры CARD пишут событие 11 при изменении срока действия и ACTIVE
    (db/06_parsec_queue_card_11.sql).

4.0.0 — 25.10.2026
--------------------------------------------------------------------------------

Переход с чужой таблицы CARDINDEV на собственную очередь PARSEC_QUEUE
(Firebird 1.5, dialect 3, WIN1251):
  * события пишут триггеры, привязка к устройствам (device/servertype) при чтении
    очереди больше не нужна;
  * строки не удаляются: PARSEC_QUEUE + PARSEC_QUEUE_LOG, статусы 0–6,
    dead letter (статус 4) виден запросом, ничего не пропадает молча;
  * каждая попытка пишется в историю: статус, код и текст ошибки, длительность,
    идентификатор worker;
  * глобальный стоп на первой ошибке сохранён, пауза ErrorTimeoutMinutes (1 мин);
  * повторная доставка идемпотентна: «уже существует» / «не найдено» — успех;
  * SQL и описание очереди — db/README.md.
